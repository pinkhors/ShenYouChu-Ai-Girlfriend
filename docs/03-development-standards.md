# ShenYouChu AI Girlfriend — 开发规范

- 版本：v0.1
- 适用：所有贡献者（含 AI 辅助开发）
- 配套：[PRD](./01-product-requirements.md)、[技术路线](./02-technical-roadmap.md)、[数据与接口契约](./contracts/data-and-interface-contracts.md)

规范的目标是让改动可预测、可审查、可回滚。文中"必须"为门禁项，"建议"为默认做法，偏离需在 PR 说明理由。

## 1. 目录结构

```text
.
├── apps/
│   └── desktop/                # Electron + React + TypeScript
├── services/
│   ├── core/                   # Spring Boot：对话/记忆/活动/认证（初期同进程分模块）
│   ├── vision/                 # Python：MediaPipe 推理与信号发布
│   └── media/                  # 媒体服务配置与集成（不自研 SFU）
├── contracts/                 # OpenAPI / WS 事件 schema / 适配器契约
├── docs/
│   ├── 01-product-requirements.md
│   ├── 02-technical-roadmap.md
│   ├── 03-development-standards.md
│   ├── contracts/
│   └── adr/                    # 架构决策记录
├── docker-compose.yaml        # 本地开发基础设施（MySQL/Redis/MinIO/Milvus）
├── .env.example               # 环境变量模板，真实 .env 不入库
├── scripts/                   # 开发与发布脚本
├── tests/                     # 跨服务端到端与隔离测试
├── CONTEXT.md
└── README.md
```

约束：

- 业务代码不放在仓库根目录；
- 临时脚本、抓取数据、模型权重、录像样本不入库；
- 真实密钥只存在于本地 `.env` 或部署密钥管理，仓库只提交 `.env.example`；
- 新增顶层目录需在 PR 中说明并在本文件登记。

## 2. 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 目录/文件（通用） | kebab-case | `turn-orchestrator.ts` |
| React 组件文件 | PascalCase | `ConversationPanel.tsx` |
| TypeScript 变量/函数 | camelCase | `cancelTurn()` |
| TypeScript 类型/接口 | PascalCase，不加 `I` 前缀 | `VisualSignal` |
| Java 类/接口 | PascalCase | `TurnOrchestrator` |
| Java 方法/变量 | camelCase | `cancelTurn()` |
| Java 常量 | UPPER_SNAKE_CASE | `MAX_RETRY` |
| Python 模块/函数/变量 | snake_case | `publish_signal()` |
| Python 类 | PascalCase | `VisionWorker` |
| 数据库表/列 | snake_case | `activity_events.user_id` |
| REST 路径 | kebab-case、复数资源 | `/api/v1/media-sessions` |
| 事件类型 | `domain.action` 小写点分 | `turn.cancelled` |
| 环境变量 | UPPER_SNAKE_CASE | `MILVUS_URI` |

补充规则：

- 布尔值用 `is/has/can/should` 前缀；
- 时间字段统一 `xxxAt`（`createdAt`）；日期字段用 `xxxDate` 仅在确需日期语义时；
- ID 字段统一 `xxxId`，不混用 `id` 与 `uuid` 命名；
- 避免缩写除公认项（`id`、`url`、`api`、`tts`、`asr`）。

## 3. 代码风格

### 3.1 通用

- 语言优先使用各自官方格式化工具，禁止手工对齐；
- 单文件保持聚焦，超过约 400 行考虑拆分（生成文件除外）；
- 错误不得静默吞掉：要么处理、要么记录并上抛；
- 公共接口必须有文档注释说明不变量、错误模式与并发/超时语义；
- 注释解释"为什么"，不复述"做了什么"。

### 3.2 TypeScript / React

- 启用 `strict`；不使用 `any`，确需时用 `unknown` + 类型守卫；
- 组件只负责渲染与交互，业务逻辑放 hooks 或独立模块；
- 服务端状态与 UI 状态分开管理；
- 所有异步请求处理加载/成功/失败/取消四态。

### 3.3 Java

- Java 21；使用 `record` 表达不可变 DTO；
- 领域层不依赖 Web/持久化框架类型；
- 依赖注入用构造器注入，不用字段注入；
- 禁止在事务内调用外部模型 API。

### 3.4 Python

- 类型标注覆盖公共函数；使用 Ruff 格式化与静态检查；
- 不在导入时执行重活（模型加载放显式初始化）；
- 视觉循环必须有超时与丢帧策略。

### 3.5 格式与静态检查

- 前端：ESLint + Prettier；
- 后端：Spotless（或等价）+ Checkstyle 规则集；
- Python：Ruff + mypy（渐进严格）；
- CI 必须包含格式化检查；本地建议配置 pre-commit；
- 具体版本与规则集在项目初始化时锁定并写入依赖文件（见待确认项）。

## 4. 分支与提交

### 4.1 分支模型

- 主干：`main`，始终保持可构建、可测试；
- 功能分支：`feat/<scope>-<summary>`、`fix/...`、`docs/...`、`chore/...`，生命周期尽量短；
- 禁止直接推送 `main`；禁止对共享分支强推（`push --force`）；
- 禁止绕过 CI 或管理员合并。

### 4.2 提交信息

格式：

```text
<type>(<scope>): <summary>

<body 可选：动机与权衡>

<footer 可选：Closes #123 / BREAKING CHANGE>
```

- `type`：`feat` `fix` `docs` `refactor` `test` `chore` `perf` `build` `ci`；
- `scope`：模块名，如 `core/turn`、`desktop/chat`、`vision`；
- `summary`：可用中文，一句话说明结果，句末不加句号；
- 一个提交只做一件事，禁止混合无关格式化。

## 5. 代码评审

### 5.1 提交前自检（作者）

- 变更范围最小化，无调试代码、无临时密钥、无大文件；
- 新增/修改行为有对应测试；
- 涉及契约、数据模型、权限的变更同步更新文档与迁移；
- 本地跑通格式化、单元测试与相关集成测试。

### 5.2 评审关注顺序

1. **正确性**：是否满足需求与验收条件；
2. **隔离与安全**：用户归属、越权路径、密钥与敏感日志；
3. **接口质量**：接口是否足够小、调用方是否被迫了解实现细节；
4. **一致性**：命名、错误处理、状态机、时间字段是否符合规范；
5. **可测试性**：依赖是否可注入、是否便于替换与模拟；
6. **可运维性**：超时、重试、取消、降级、可观测。

### 5.3 评审规则

- 至少 1 名维护者批准；涉及认证、数据删除、媒体权限、搜索与运营检索权限的变更需 2 人；
- 评审意见分「必须修改 / 建议 / 提问」，作者逐条回应；
- 大改动先提交设计说明或 ADR，再进入实现；
- 禁止在评审中要求与本次变更无关的重构，另开 PR。

## 6. 测试规范

### 6.1 分层要求

| 层级 | 要求 |
|---|---|
| 单元 | 领域逻辑、Turn 状态机、适配器映射、时间与权限判断 |
| 契约 | REST/WS schema、模型适配器输入输出、错误码 |
| 集成 | 数据库、缓存、对象存储、向量库、服务间调用 |
| 端到端 | 登录→文本→语音→打断→删除；跨用户隔离 |
| 故障 | 模型超时、ASR 断流、媒体断开、存储不可用降级 |
| 性能 | 首音延迟分位、视觉 FPS、取消生效时间 |

### 6.2 必须覆盖的场景

- 中间 ASR 稿不触发回答；迟到的 final 不触发已取消轮次；
- 取消后旧序号音频不播放；
- 记忆检索超时降级且不阻塞；
- 用户 A 不能读取/进入/下载/取消用户 B 的任何资源；
- 搜索永远不返回他人内容；运营检索缺少角色或事由时被拒绝，且成功检索必有审计事件；
- 删除账号后 MySQL/Redis/Milvus/MinIO/任务均无残留（矩阵逐项验证）；
- 低置信度视觉信号不进入提示词。

### 6.3 覆盖率与数据

- 核心领域与状态机覆盖率门禁值在项目初始化时锁定（候选：行/分支 80%）；
- 不以覆盖率替代行为断言；
- 测试数据使用合成数据或明确授权的样本，禁止使用真实用户视频/对话。

### 6.4 测试运行约定

- 单元与契约测试：每次 PR 必须通过；
- 集成与端到端：合入主分支必须通过；
- 性能与故障演练：里程碑执行，报告归档到 `docs/` 或 CI 制品；
- 允许标记不稳定的测试但必须有跟进 issue，禁止静默删除。

## 7. 配置与密钥

- 所有可变配置来自环境变量或配置文件，禁止在代码中写死地址、模型 ID、桶名；
- `.env.example` 提供全部键名与占位值，不含真实凭据；
- 前端不得持有任何后端/模型/存储密钥；
- 密钥泄露应急：立即轮换并记录事件，不通过改写历史提交掩盖；
- 本地默认值必须显式标注"仅开发"，生产环境缺失必填配置时启动失败。

## 8. 数据库与迁移

- 所有 schema 变更通过版本化迁移提交，禁止手工改生产库；
- 迁移必须可前滚；破坏性变更分两步（先扩展、后收缩）；
- 每个业务表必须包含 `created_at / updated_at / deleted_at`，事件类表另含 `occurred_at`；
- 迁移评审关注：索引、锁表风险、回滚路径、数据回填对线上延迟的影响；
- 查询必须带用户归属条件；新增表需在契约文档登记。

## 9. 接口、事件与实时任务

- 契约先行：新增/修改 REST、WS 事件、内部信号必须更新 `contracts/` 并过契约测试；
- 所有实时消息携带 `turnId`、`sequence`、`schemaVersion`，接收端丢弃过期序号；
- 取消是幂等操作，可重复调用；
- 跨服务调用必须重新校验资源归属，不信任上游传入的身份声明；
- 事件发布失败不得阻塞主链路，但必须可重试且可观测。

## 10. 日志、可观测与隐私

- 结构化日志，字段包含 `traceId`、`userId`（内部 ID）、`conversationId`、`turnId`、`eventType`、耗时；
- **禁止记录**：完整对话正文（应通过 ID 关联）、音频、视频帧、关键点数组、密钥、Token、签名 URL；技术日志中不记录用户搜索词与运营检索查询明文（审计事件只存查询哈希与命中统计）。
- 用户可识别信息最小化；生产日志按保留期清理；
- 关键链路必须埋点：ASR 首字/最终、检索耗时、LLM 首 token、TTS 首帧、客户端可听首音、取消生效时间；
- 指标与追踪接入方式在部署阶段确定，本地开发可用控制台输出替代。

## 11. 依赖与开源许可

- 新增依赖需说明用途、维护状态与许可证，禁止引入不明来源二进制；
- 依赖锁定版本并提交锁文件；定期升级与漏洞扫描；
- 模型权重、音色、立绘、字体、SDK 的许可证单独核查，代码开源不等于素材可商用；
- 项目许可证在初始化时确定（见待确认项），贡献者需遵守 CLA/DCO 约定（如启用）。

## 12. 发布与回滚

- 环境：local → staging → production，同一镜像逐级晋级；
- 版本号遵循语义化版本；发布说明列出变更、迁移与已知问题；
- 发布流程：跑端到端与隔离测试 → 备份/确认迁移 → 部署 → 观察延迟与错误率；
- 回滚：保留上一可用镜像与迁移回滚路径；数据破坏性变更禁止无备份发布；
- 发布后若隔离或删除相关测试失败，立即回滚并阻断后续发布。

## 13. Definition of Ready / Done

**Ready（进入开发前）**：需求有 FR 编号与验收条件；接口/数据变更已更新契约；依赖与风险已知；测试方式明确。

**Done（完成）**：

- 验收条件通过，含自动化测试；
- 契约与文档同步更新；
- 无调试残留与密钥；
- 隔离、取消、超时降级已验证；
- 有可观测埋点；
- 经评审合入主分支并可回滚。

## 14. 文档维护

- 行为或接口变化必须同步文档，文档与代码同一 PR；
- 重要且难以回退的架构决策写 ADR（`docs/adr/NNNN-title.md`），内容：背景、选项、决策、后果；
- `CONTEXT.md` 只维护术语，不写实现细节；
- 本规范自身变更需评审并记录在 PR 中。
